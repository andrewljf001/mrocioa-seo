# MROCIOA Web Serial Debugger 发行规范

本文档是 Web Serial Debugger 后续升级、测试、发行、同步和回退的长期规范。

## 1. 基本原则

- 修改时一次只完成一个定义清楚的问题，避免同时改动无关功能。
- 每个问题必须先在本地完整实现并单独验证，再进入候选发行范围。
- 不要求每完成一个问题就立即上线。正常情况下，将 1–3 个已经完成且风险相关的问题合并为一个小版本发行。
- 紧急故障、安全问题或影响主要功能的问题可以单独发行补丁版本。
- 线上只允许出现正式稳定版本，不显示 `dev`、`debug`、`beta`、内部构建号或调试阶段记录。
- 串口工具之外的页面不属于默认修改范围；任何跨页面改动必须另外确认。

## 2. “一个完整问题”的定义

一个问题只有同时满足以下条件，才算完成：

1. 用户目标和边界已经确认。
2. 主功能已经实现。
3. 相关视觉、异常处理和回退行为已经处理。
4. Chrome 和 Microsoft Edge 本地验证通过。
5. 不支持 Web Serial 的浏览器仍正确显示 Chrome/Edge 提示，且不加载工具界面。
6. 未破坏串口连接、日志、导出、图表、协议解析和已有用户设置。
7. 用户完成验收，或明确授权按已确认的结果发行。

例如，“真正的全屏”是一个完整问题，其范围应包括：

- 用户点击后进入真正的浏览器全屏，而不是只打开新标签页。
- Header、Hero、产品轮播和 Footer 不出现在全屏画面中。
- Chrome/Edge 的地址栏和标签栏在全屏时隐藏。
- 普通、独立和全屏模式的颜色保持一致。
- `Esc` 和页面退出控件都能正常退出全屏。
- 进入或退出全屏不会丢失串口会话、日志和设置。
- Fullscreen API 不可用或被拒绝时，自动退回网页沉浸模式。

## 3. 版本号规则

项目采用语义化版本号：

```text
MAJOR.MINOR.PATCH
主版本.次版本.补丁版本
```

| 类型 | 使用条件 | 示例 |
| --- | --- | --- |
| PATCH | 修复错误、补全原本承诺的行为、颜色或交互一致性修正、兼容性修复，不造成不兼容变化 | `1.0.1` |
| MINOR | 新增明显的用户功能，同时保持已有配置和工作流兼容 | `1.1.0` |
| MAJOR | 大规模重构、用户数据或配置不兼容、核心工作流或权限模型发生破坏性变化 | `2.0.0` |

当前首次正式发行的规范版本号为 `1.0.0`，界面中的历史显示名为 `Release 1.0`。从下一个版本开始，界面、发行记录和 Git 标签应显示完整版本号，例如 `Release 1.0.1`。

版本号只在正式候选范围冻结后更新，不因每次代码编辑而递增。

## 4. 版本号的单一来源

- `serial-tool-source/VERSION` 是规范版本号的唯一来源。
- 构建流程必须从 `VERSION` 读取版本号并写入工具界面。
- `CHANGELOG.md` 只记录已经正式发行的版本。
- 未发行的修改记录在任务说明、Git 分支、提交记录或发行检查表中，不写入线上 Changelog。
- 正式发行使用 Git 标签：`serial-tool-v<完整版本号>`，例如 `serial-tool-v1.0.1`。
- `wp/VPS-SOURCE-SHA256.txt` 保存线上正式文件的 SHA-256。
- 页面使用的 `filemtime` 或缓存查询参数只负责刷新缓存，不能代替正式版本号。

## 5. 环境职责

| 环境 | 职责 |
| --- | --- |
| 本地源码 | 开发、逐问题修改、代码审查和版本准备 |
| 本地发行包 | 浏览器交互、视觉、兼容性和回归验证 |
| VPS | 当前线上正式运行版本的生产权威副本 |
| GitHub `main` | 已发行源码、发行文档、校验记录和可追溯历史 |

开发中的未完成内容不得覆盖 VPS 正式文件，也不得作为正式发行内容进入 GitHub `main`。

## 6. 标准发行流程

1. **确定范围**：列出本次版本包含的问题，以及明确不包含的内容。
2. **逐问题实现**：每次只修改一个完整问题，并保留独立验证结果。
3. **本地回归**：使用全新浏览器状态验证默认英文、Chrome/Edge、浏览器限制、串口主要功能和视觉一致性。
4. **用户验收**：提供本地页面或截图，由用户确认发行结果。
5. **冻结版本**：确定 PATCH、MINOR 或 MAJOR，并更新 `VERSION`。
6. **写发行记录**：在 `CHANGELOG.md` 中加入正式日期、功能记录、兼容性和隐私说明。
7. **生成发行包**：构建过程必须可重复；相同源码和版本应生成相同内容。
8. **发行检查**：确认发行包不包含旧版本号、调试文字、测试记录或未批准功能。
9. **计算校验值**：保存发行包 SHA-256，并与候选文件核对。
10. **建立回退点**：在 VPS 替换前备份当前正式文件；如涉及模板、菜单或数据库，同时建立相应备份。
11. **部署 VPS**：只部署本次范围内的文件。
12. **精准刷新缓存**：只刷新相关页面和资源，避免影响其他页面。
13. **线上验证**：检查 HTTP 状态、SEO 页面、Chrome/Edge、浏览器限制、正式版本号和核心功能入口。
14. **三地同步**：以 VPS 正式文件回同步本地镜像，再更新 GitHub 的发行源码和校验清单。
15. **提交和标记**：提交 GitHub、推送 `main`，创建 `serial-tool-v<版本号>` 标签。
16. **完成报告**：记录 VPS、本地和 GitHub 三份发行包的 SHA-256，三者必须一致。

## 7. 每次发行的最低测试范围

- 首次访问默认语言为 English。
- 用户已经保存的语言、快捷命令和工具设置不会被意外清除。
- Chrome 与 Microsoft Edge 能加载应用并显示 Web Serial 功能入口。
- Firefox、Safari 等不支持的浏览器只显示指定提示，不直接显示工具。
- 串口授权、连接、断开、自动重连和多会话入口正常。
- ASCII/HEX 收发、快捷发送、循环序列、文件发送入口正常。
- 监视、搜索、清空、记录和导出入口正常。
- 图表、CSV/PNG 导出和协议解析入口正常。
- Header、Footer、Hero、产品轮播和 TOOLS 菜单未被意外改变。
- 页面 SEO 标题、描述、Canonical、结构化数据和 Sitemap 状态未退化。
- Release Changelog 只显示正式版本。

涉及 Web Serial 真实硬件行为的发行，必须额外完成至少一台实际设备的连接、收发和断线重连测试。

## 8. 正式发行记录格式

每个版本至少记录：

- 完整版本号和发布日期。
- 状态：Stable。
- Added、Changed、Fixed 中适用的项目。
- Chrome/Edge 兼容性说明。
- 本地处理、不上传设备数据的隐私说明。
- 发行包 SHA-256。
- VPS 回退文件路径。
- 本地和线上 QA 结果。
- Git 提交和 Git 标签。

## 9. 回退规则

- 每次正式部署前都必须保存当前线上发行包。
- 回退文件名必须包含旧版本号或发布日期，不能使用含义不明确的 `backup-final`。
- 至少保留最近两个正式版本的可部署发行包；串口工具单文件发行包建议长期保留。
- 出现无法连接、数据异常、页面空白、严重视觉错误或浏览器限制失效时，应优先回退，不在生产环境直接调试。
- 回退后同样需要精准刷新缓存并验证公网结果。

## 10. Git 与安全边界

- `main` 只保存已发行或已经确认可发行的内容。
- 开发工作使用独立分支，建议命名为 `codex/serial-tool-<问题或版本>`。
- 不提交 WordPress 数据库、服务器凭据、API 密钥、缓存、用户上传、付费父主题或商业插件。
- GitHub 中的正式独立发行包必须与 VPS 和本地镜像的 SHA-256 一致。
- 任何三地不一致都视为同步未完成，不能宣布发行结束。

## 11. 推荐发行节奏

- 日常小修：完成并验证 1–3 个相关问题后发行一个 PATCH。
- 重要故障：单独发行 PATCH，不等待其他问题。
- 明显新功能：汇总到 MINOR 版本，但仍逐问题实现和验收。
- 不为文案标点、内部注释或未部署的开发提交单独增加正式版本号。

当前建议的下一版本是 `1.0.1`。其具体范围必须在修改开始前单独确认，未确认的功能不得自动加入。
